# 全体設計と段階的な実装

## 第一段階：今回のデザイン確認

ブランド仮名「整体室 余白」。ターゲットは20〜40代の働く世代。アイボリー #F7F5F1、サンド #C7B9A7、文字 #282A2C、アクセント #B39A75。アクセント色は装飾に使い、小さな文字には濃い色を使う。予約と料金は常に発見しやすく、初回の流れとFAQで不安を減らす。

トップの順番は、ヘッダー→メインビジュアル→通いやすさ→メニュー・料金→初回の流れ→スタッフ→FAQ→アクセス・営業時間→予約案内・フッター。メインビジュアルの後に短いお知らせを置く。

今回はトップページのみを実装し、予約を受け付けず、デザイン確認で区切る。8つのページを完成したように見せる仮リンクは作らない。

## 第二段階：固定ページと予約の設計

予定ルート：

| ルート | 内容 | 今回の状態 |
| --- | --- | --- |
| `/` | トップ | 実装済み |
| `/menu` | 施術メニュー・料金 | トップの料金・詳細表示で確認 |
| `/first-visit` | 初めての方へ | トップの流れで確認 |
| `/staff` | スタッフ紹介 | トップの紹介で確認 |
| `/access` | アクセス・営業時間 | トップの仮表示で確認 |
| `/faq` | よくある質問 | トップの開閉で確認 |
| `/reservation` | WEB予約 | 未実装・準備中案内 |
| `/privacy` | 正式なプライバシーポリシー | 未実装・現段階の案内のみ |
| `/admin/*` | スタッフ専用管理画面 | 未実装 |

メニュー、料金、営業時間、休み、スタッフを確定。予約の受付期限、施術前後の準備時間、最終受付、指名可否、変更・キャンセルの期限や料金を先に決める。病歴など不要な情報は収集せず、自由記入欄にも不要な機微情報を入力しない案内を付ける。

## 第三段階：予約・データベース

Next.js App Router＋TypeScript＋Tailwindを継続。Supabase Postgres・Auth、Vercel、メール配信先は承認後に設定。現段階では接続も契約もない。

- 将来の予約受付には静的エクスポート設定を外し、Next.jsのサーバー処理を使う。
- テーブル候補：menus、staff、staff_shifts、opening_hours、closures、reservations、notifications、announcements、audit_logs。IDと更新時刻、公開状態、料金・時間のスナップショットを持つ。
- 顧客側は公開メニュー・営業時間と匿名の空き枠のみ取得。予約一覧や氏名・連絡先を取得できる権限を与えない。
- 認証済みでもスタッフ権限がなければ管理API・管理ページ・データを返さない。リンクを隠すだけの管理画面にしない。
- 全表でRLSを有効化し、最小権限で許可。スタッフ権限は本人が変更できないサーバー管理の役割で確認。service roleなどの秘密はサーバー環境変数だけで管理する。
- 空き枠表示と予約確定は分離。サーバーで営業時間・シフト・臨時休業・準備時間・施術時間を再検証。
- 予約の占有時間を `[開始,終了)` とし、有効な予約同士をPostgresの排他制約等で競合防止。確認ボタンの連打・再送には冪等キーを使用。トランザクションで確定し、競合時は別枠の選び直しを案内する。
- 変更・キャンセルは、期限付きの推測できない管理用トークンまたは本人認証で許可。トークンは平文保存しない。変更時も新しい時間との競合・権限を再検証。
- 予約を先に確定し、通知は再試行可能な処理に分離。メール失敗時も二重の予約を作らず、送信結果を追跡する。
- 日時はDBではタイムゾーン付きで保存し、表示・営業判定はAsia/Tokyoに統一する。

## 第四段階：管理画面・保護

管理者ログイン、予約一覧・検索、変更・キャンセル、営業時間・定休日、メニュー・料金、シフト、臨時休業、お知らせを追加。変更者・操作・時刻・対象IDを監査記録に残し、ログに個人情報を無駄に含めない。

管理者と一般スタッフの権限は役割表で定義し、URL直打ち・API直接呼び出しも拒否する。管理者の多要素認証、セッション管理、サーバー検証、CSRF対策、メール送信制限、レート制限・スパム対策を実装する。確認メールは架空のテスト宛先から開始し、実在の顧客情報は使わない。

## 最終段階：納品・運用

- データ保持期間・問い合わせ窓口・委託先を確定し、実態に合ったプライバシーポリシーを作る。
- 利用するDBプランのバックアップ保持期間・PITR対応を確認し、必要に応じた暗号化バックアップを用意する。
- 具体的な復元手順、障害時の窓口、リリースの戻し方、目標復旧時間を運用文書に書き、検証環境で復元を試す。
- 権限外アクセス、二人同時予約、連打、タイムアウト、メール失敗、当日変更、シフト変更と既存予約の競合をテストする。
- 秘密鍵・認証情報・アクセス制御は納品前に別途レビューする。公開URL・ドメイン・費用を提示して承認を得てから本番公開する。

上記の本番用処理は設計方針であり、今回のトップページに実装済みという意味ではない。
